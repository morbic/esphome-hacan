= HACAN protocol specification
:toc: left
:sectnums:

Status: *Draft, version 1.0.0-draft.1*

HACAN (Home Automation over CAN) is an application protocol for distributed home
automation nodes connected by Classical CAN. This specification is independent
of ESPHome and is intended to be implementable on other embedded platforms.

The keywords *MUST*, *MUST NOT*, *REQUIRED*, *SHOULD*, *SHOULD NOT*, and *MAY*
are to be interpreted as described by RFC 2119 and RFC 8174 when, and only when,
they appear in uppercase.

The architecture decisions referenced by this draft are accepted project
directions. The protocol remains a draft: its wire details may change until the
first implementation has been tested in a representative physical installation.

== Design status

The established project constraints are: CAN as transport, independence from
ESPHome, support for approximately 100 to 200 field modules and several main
devices, active branching, local operation during central-service outages,
event-oriented traffic, deterministic embedded behavior, and future-compatible
extension.

The accepted baseline includes Classical CAN, 29-bit identifiers, the bit
layout, 9-bit addresses, fixed payload schemas, event-driven communication,
commissioned addressing, active bridges, a distributed entity directory, and a
physically trusted security model.

Before the draft can become version 1.0.0, an implementation must validate the
codec, timing, discovery, entity resolution, conflict behavior, restart load,
and bridge behavior on representative hardware and wiring. The first endpoint
profiles and actuator failure policies also remain to be defined. Authenticated
operation, group addressing, firmware transfer, and CAN FD remain explicitly
deferred designs.

== Scope of version 1

Version 1 defines:

* Classical CAN data frames with a 29-bit extended identifier and an 8-byte
  payload;
* global node addresses, local endpoint identifiers, and installation-scoped
  logical entity identifiers;
* state, event, command, request/response, configuration, discovery, time, and
  diagnostic messages;
* optional application acknowledgements with bounded retries;
* active forwarding between CAN segments arranged as a tree;
* compatibility and extension rules.

Version 1 does not define automated EntityId allocation, firmware transfer,
generic payload fragmentation, dynamic endpoint schemas, authentication,
encryption, or an ESPHome/Home Assistant entity mapping. These are deliberate
exclusions, not implied features.

== Conformance

A conforming implementation MUST implement the identifier validation rules,
address rules, byte order, unknown-value handling, and restart behavior in this
specification. Features explicitly marked optional need not be implemented, but
an implementation MUST advertise optional capabilities accurately.

A bridge is also a node and MUST satisfy both the node and bridge requirements.
