== Design goals

HACAN is designed for 100 to 200 small embedded nodes, several controller or
actuator nodes, and active branches made of separate CAN segments. It favors
deterministic behavior, bounded memory use, peer-to-peer operation, and traffic
generated by changes rather than polling.

The protocol does not assign a privileged role to Home Assistant, ESPHome, or a
central controller. Any commissioned node may publish values or address a
command to another node. Installation policy decides which nodes are allowed to
do so.

== Communication model

HACAN uses a mixed communication model:

* `STATE` publishes the latest value of an endpoint. It is normally sent after
  a change and in response to `GET_STATE`.
* `EVENT` reports an occurrence such as a button press. An event is not a stored
  state and MUST carry a new sequence number for each occurrence.
* `COMMAND` asks an endpoint to perform an action or assume a value.
* `REQUEST` and `RESPONSE` provide bounded request/response operations.
* discovery, configuration, time, and diagnostics use dedicated message kinds.

Normal operation is event-driven. Nodes MUST NOT periodically republish all
states merely to indicate liveness; `HEARTBEAT` exists for that purpose.

== Nodes and endpoints

A node is one physical or logical participant with one installation-wide short
transport address. An endpoint is a function within that node, for example a
digital input, relay, temperature channel, or status LED.

Node addresses are global across all actively bridged segments. Endpoint
identifiers are local to a node. The pair `(node address, endpoint identifier)`
addresses a function at the current time but is not its stable semantic
identity. An installation-scoped `EntityId` identifies the logical function and
is resolved to the current node and endpoint through the distributed directory;
see xref:entities.adoc[Logical entities and distributed directory].

CAN supplies arbitration, frame integrity, transmitter retry, and error
confinement on one electrical segment. HACAN supplies application addressing,
semantics, optional application acknowledgement, discovery, and forwarding
between independent segments.

An application acknowledgement is distinct from the CAN ACK slot. The CAN ACK
slot only proves that at least one controller received a valid frame on the
current segment.

== Physical and data-link profile

HACAN version 1 uses:

* ISO 11898-2 high-speed CAN physical signaling;
* Classical CAN 2.0B extended data frames;
* a nominal bit rate of 125 kbit/s;
* exactly 8 data bytes per HACAN frame;
* normal CAN retransmission and error confinement.

Every electrical segment MUST be a valid CAN bus with termination at both ends.
Passive star branches are outside the profile. A branch is created with an
active bridge and is a separate terminated CAN segment.

125 kbit/s is the version 1 installation default, not a universal cable-length
guarantee. Cable type, topology, transceivers, isolation, propagation delay,
stub length, and EMC conditions still require engineering validation. A closed
installation MAY use another nominal rate if every node on that segment is
configured identically; discovery of bit rate is not defined.

Standard identifiers, Remote Transmission Request frames, error frames exposed
as application messages, CAN FD frames, and payload lengths other than 8 are
not HACAN version 1 frames and MUST NOT be decoded as HACAN.

== Local autonomy

The wire protocol enables local autonomy but does not define a rule engine.
Nodes MAY store local bindings or rules expressed using EntityIds and exchange
`EVENT`, `STATE`, and `COMMAND` messages without an online gateway. The volatile
entity directory resolves those bindings to compact transport addresses.
Failure behavior of an actuator is endpoint-specific configuration; no
universal safe output value is assumed.

== Deliberate constraints

The fixed frame size avoids allocation and reassembly state. Human-readable
names, long strings, certificates, firmware images, and other bulk data do not
fit in version 1. Such data belongs in an explicitly designed future transport,
not in undocumented sequences of frames.
