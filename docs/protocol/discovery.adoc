= Discovery and commissioning
:toc: left
:sectnums:

== Overview

Discovery reports nodes already present on the installation. Commissioning
assigns a short persisted transport address to a Node UID. The manager MAY
select the address automatically from the unused address space. The address is
not semantic identity and may later be reassigned. These operations do not
require a permanently online controller, but assigning addresses requires a
temporary commissioning manager.

== Discovery request and response

`DISCOVERY_REQUEST` is broadcast by a commissioned requester or an unassigned
node. An unassigned requester uses source zero.

[cols="1,2,4",options="header"]
|===
|Byte |Field |Meaning
|B0 |Transaction |Chosen by requester.
|B1 |Flags |Bit 0 include commissioned; bit 1 include unassigned; bit 2 request
`ANNOUNCE`; others zero.
|B2..B3 |Window |Response window in milliseconds, `UINT16`; 1000..10000.
|B4..B7 |Challenge |Requester-selected `UINT32` used to spread responses.
|===

Each matching node schedules exactly one response within the requested window.
The delay SHOULD be a deterministic hash of Node UID and challenge modulo the
window, plus small local timer jitter. This makes retries with a new challenge
redistribute collisions.

An unassigned node sends its first request after a UID-derived delay from 0 to
1000 ms. Without a matching `ADDRESS_ASSIGN`, it retries with a new transaction
and challenge after 2, 4, 8, and 16 seconds, then every 30 seconds.

This is an alternative discovery flow. The unassigned requester also schedules
one `DISCOVERY_RESPONSE` for its own request within the advertised response
window. That response carries its Node UID and lets a commissioning manager
issue `ADDRESS_ASSIGN` without changing either frame layout.

`DISCOVERY_RESPONSE` is sent to the requester. A commissioned node uses its
normal source address. An unassigned node uses source zero.

[cols="1,2,4",options="header"]
|===
|Byte |Field |Meaning
|B0 |Transaction |Copied from request.
|B1..B6 |Node UID |48-bit stable identifier, least-significant byte first.
|B7 |Capabilities |Same bits as `ANNOUNCE`.
|===

The CAN arbitration behavior of two source-zero responses with the same CAN
identifier is not a collision-resolution protocol. Random response timing is
mandatory. A manager SHOULD repeat discovery with a new challenge when bus
errors occur or responses are expected to be incomplete.

== Address assignment

`ADDRESS_ASSIGN` is broadcast and has no transaction byte because all 64 payload
bits are used:

[cols="1,2,4",options="header"]
|===
|Byte |Field |Meaning
|B0..B5 |Node UID |Target stable identifier.
|B6 |Address low |Low eight bits of assigned address.
|B7 bit 0 |Address high |Bit 8 of assigned address.
|B7 bits 1..7 |Flags |Bit 1 `PERSIST`; all other bits zero.
|===

Only addresses `0x001..0x1FE` are valid. `PERSIST` MUST be set in version 1; a
node stores the address in non-volatile memory before claiming it. Repeating an
identical assignment is idempotent. A node whose UID does not match ignores the
frame.

Version 1 does not authenticate a commissioning manager. Physical access and an
installation commissioning mode are therefore RECOMMENDED; see
xref:security.adoc[Security model].

== Address claim

After loading or accepting an address, a node waits a UID-derived 0 to 2000 ms
delay and broadcasts `ADDRESS_CLAIM` using the claimed address as its source:

[cols="1,2,4",options="header"]
|===
|Byte |Field |Meaning
|B0..B5 |Node UID |Claimant stable identifier.
|B6 |Protocol major |Claimant protocol major.
|B7 |Claim nonce |Low byte of a UID/boot-token hash; collision spreading only.
|===

A node sends two claims separated by 250 to 500 ms of UID-derived jitter. It
MUST accept normal addressed traffic only after this claim period finishes
without losing conflict resolution. It then sends `ANNOUNCE` and its initial
entity claims and state snapshot as described in
xref:diagnostics.adoc[Diagnostics].

All nodes and bridges SHOULD observe claims. Seeing two UIDs use one source
address establishes a conflict. An observer sends `ADDRESS_CONFLICT` to that
address:

[cols="1,2,4",options="header"]
|===
|Byte |Field |Meaning
|B0..B5 |Winning UID |Numerically lower of the two UIDs.
|B6 |Reason |`0x01` duplicate address; other values reserved.
|B7 |Sequence |Observer sequence value.
|===

The numerically lower UID deterministically retains the address. A claimant
with a higher UID withdraws immediately to address zero, stops normal traffic,
sets `configuration required`, and waits for a new assignment. The lower UID
repeats its claim after a randomized delay. This rule restores communication;
it does not authorize automatic selection of a new address.

A node that observes an `ADDRESS_CLAIM` from another UID using its own address
applies the same comparison even if no observer sends `ADDRESS_CONFLICT`.

== Removal and address changes

There is no remote address-release message in version 1. A commissioning tool
changes an address by sending `ADDRESS_ASSIGN` for the same UID. The node stops
normal traffic, persists the new address, and repeats the claim procedure.

Factory reset and deletion of commissioning state are implementation-specific
local operations. They MUST NOT be triggered by an undocumented CAN payload.

== Entity directory discovery

Address commissioning identifies physical nodes; entity directory discovery
identifies the logical installation functions assigned to their endpoints.
After completing address claim, a node advertises every configured assignment
with `ENTITY_CLAIM`. A late-joining controller or peer uses `ENTITY_RESOLVE` to
rebuild the mappings required by its local configuration.

EntityIds are allocated in the installation registry and configured before the
owner advertises them. Version 1 does not allocate, transfer, or rename an
EntityId on the bus. See xref:entities.adoc[Logical entities and distributed
directory] for ownership, replacement, and conflict rules.

The central registry is a build-time alias-to-identifier dictionary. Ownership
is declared in node configuration, not in the registry. Runtime directory
recovery uses `ENTITY_RESOLVE` and fresh `ENTITY_CLAIM` responses; it never
downloads the registry.
