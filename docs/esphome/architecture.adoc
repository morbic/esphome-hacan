= ESPHome implementation architecture
:toc: left
:sectnums:

== Goal

The ESPHome implementation is the first HACAN implementation, not part of the
protocol definition. It must use the generic ESPHome `canbus` API and support
ESP32 Arduino and ESP-IDF without directly calling framework-specific CAN
drivers.

The implementation separates the portable protocol library from the ESPHome
adapter. Neither the codec nor node behavior may depend on ESPHome, Arduino,
ESP-IDF, heap allocation, or blocking operations.

== Source layout

----
components/hacan/
  __init__.py
  hacan.h
  hacan.cpp
  binary_sensor/
  switch/
  protocol_*.h
  protocol_*.cpp
  protocol/
    tests/
    CMakeLists.txt
----

The protocol sources are physically in the component root so ESPHome copies
them into its generated build project. The CMake test target remains under
`protocol/`. The library is logically independent: it uses only standard C++,
has host tests, and can later be extracted without changing its public API.

== Runtime flow

----
ESPHome CAN callback -> HacanComponent -> NodeRuntime -> FrameCodec
                                        <- generated RawCanFrame
                                        -> ESPHome CAN transmitter
----

`HacanComponent` is an adapter. It receives and transmits CAN frames through
the public ESPHome API, obtains monotonic time, and stores the commissioned
address using ESPHome persistent preferences. It does not encode payload bytes
or own protocol state machines.

Configured entities and `NodeRuntime` are stored in fixed-capacity in-place
storage. The ESPHome `canbus` API itself requires `std::vector<uint8_t>` for
its callback and transmit signatures; that API-bound conversion is the only
dynamic container at the adapter boundary. The portable protocol path has no
heap allocation.

`NodeRuntime` owns commissioning, address claim and conflict behavior,
heartbeat scheduling, the volatile entity directory, duplicate tracking,
bounded transmit queues, and dispatch of application frames. It is called with
an explicit time value through `tick(uint32_t now_ms)` and therefore creates no
timers and performs no blocking wait.

`FrameCodec` is the sole byte-level boundary. It converts a validated
`RawCanFrame` to a `ProtocolFrame` and converts a `ProtocolFrame` to a
`RawCanFrame`. It implements all message kinds allocated by protocol version
1, including kinds whose active runtime behavior is deferred.

== Frame model

`CanIdentifier` is a value object for the 29-bit HACAN identifier.
`RawCanFrame` contains that identifier, the extended-frame flag, DLC, and eight
data bytes. `ProtocolFrame` composes a `CanIdentifier` and a tagged
`PayloadVariant`.

Every concrete payload type owns its fields and knows how to encode its exact
eight-byte representation. `PayloadVariant` is a `std::variant` over those
payload types. This gives the codec one generic encode/decode API without
dynamic allocation, virtual ownership, or lifetime ambiguity. It is preferable
to an `IFrame` hierarchy whose base object would require pointers or a manual
placement buffer to own derived payloads.

Decoding returns either a complete `ProtocolFrame` or a specific `DecodeError`.
It does not throw exceptions and never exposes a partially decoded payload.
Valid but unrecognized future kinds are distinct from malformed frames so the
runtime can update `rx_unknown_kind` rather than `rx_malformed`.

== Protocol ports

`NodeRuntime` receives small abstractions for its environment:

* `IFrameTransmitter` accepts completed `RawCanFrame` values.
* `IAddressStorage` loads and durably saves the commissioned `NodeAddress`.
* `INodeEvents` receives entity-directory changes for local consumers.
* `IEndpointHandler` accepts an addressed command for one local endpoint and
  returns a protocol `Status`.

The ESPHome adapter implements these ports. Host tests replace them with simple
fakes, making lifecycle and recovery behavior deterministic without ESP32
hardware.

== Endpoint boundary

Endpoint platforms explicitly declare their owned EntityId and EndpointId to
`HacanComponent`; ownership is then registered in `NodeRuntime` before normal
operation begins. The runtime does not infer ownership from arbitrary Home
Assistant entities. A `COMMAND` addressed to an unregistered endpoint returns
`UNSUPPORTED`; duplicate commands reuse their initial acknowledgement status
without invoking the handler again.

The first two profiles are deliberately narrow:

* `binary_sensor: platform: hacan` mirrors an existing local binary sensor and
  publishes its changes as `STATE<bool>`.
* `switch: platform: hacan` owns a local `output`, applies received
  `COMMAND<bool>`, and publishes the resulting `STATE<bool>`. Its optional
  state-source subscription is represented by a portable `IStateListener`;
  one source entity may therefore fan out to many local switch outputs.
* `hacan.publish_event` sends a local ESPHome-recognized button gesture. Each
  `event_sources` item is a portable listener binding, allowing one event to
  drive multiple local switch or light actions.
* `light: platform: hacan` is a binary `ON_OFF` light backed by a local output,
  `COMMAND<bool>`, and `STATE<bool>`.

== Queue policy

The component has separate fixed-capacity queues for control, event,
state/query, management, and diagnostic traffic. Their capacities are generated
from YAML at firmware build time and implemented with `std::array`; no runtime
heap allocation occurs. A full queue never evicts a frame in another traffic
class. Only a pending `STATE` for the same endpoint may be superseded by a newer
state. Commands and events are never coalesced.

The transmitter drains higher CAN priorities before lower ones. Queue drops are
reported through `tx_queue_drops`.

== Base diagnostics

`HacanComponent` exposes structured C++ accessors for accepted received frames,
malformed received frames, and successfully transmitted frames. `dump_config()`
also logs these counters, the persisted NodeAddress, and configured entity
counts. At ESPHome `INFO` level, every transmitted and received HACAN frame is
logged with its raw CAN identifier, CAN flags, DLC, priority, message kind,
destination, source, hop count, and all eight data bytes. Rejected frames are
logged as rejected as well. ESPHome diagnostic entities and protocol
`DIAGNOSTIC_REQUEST` handling remain deferred.
