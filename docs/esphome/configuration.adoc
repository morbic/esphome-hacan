= ESPHome YAML configuration
:toc: left
:sectnums:

This page specifies the available configuration interface for the HACAN base
component.

== Central entity registry

An installation keeps the alias-to-identifier registry in one YAML file. It is
included using standard ESPHome packages and substitutions. ESPHome expands the
substitution before validating the HACAN configuration; the component therefore
receives a numeric identifier and has no YAML registry parser.

[source,yaml]
----
# installation/entities.yaml
substitutions:
  hacan_living_room_main_light_switch: "0x01010001"
  hacan_living_room_main_light: "0x01020001"
----

The registry is a build-time installation artifact. It contains neither node
identity nor endpoint ownership and is never transmitted or refreshed at
runtime. Installation policy should prohibit local redefinition of these
substitutions.

== Base component

[source,yaml]
----
packages:
  hacan_entities: !include installation/entities.yaml

hacan:
  canbus_id: hacan_bus
  commissioning_role: primary  # primary | secondary | none
----

`NodeUID` is derived deterministically from the ESP32 factory MAC address. No
YAML override is provided in the first implementation. A `NodeAddress` is
assigned by commissioning and persisted locally by the component.

The base component does not declare entities. HACAN endpoint platforms own
their declared `entity_id` and `endpoint` automatically. A platform property
that consumes a remote entity, such as `state_source_entity_id`, automatically
registers it for `ENTITY_RESOLVE`; an owning node replies with `ENTITY_CLAIM`.

== Binary sensor endpoint

`binary_sensor: platform: hacan` mirrors a pre-existing local binary sensor.
The source input retains responsibility for pin configuration and input
filtering. The HACAN endpoint owns the declared EntityId and emits one
`STATE<bool>` after every reported source change. It does not emit `EVENT`.

[source,yaml]
----
binary_sensor:
  - platform: gpio
    id: in01
    pin:
      number: GPIO14
      mode: INPUT_PULLUP
      inverted: true
  - platform: hacan
    id: hacan_in01
    hacan_id: hacan_node
    source_id: in01
    entity_id: 0x01010001
    endpoint: 0x01
    internal: true
----

`id` is required by ESPHome even when `internal: true` hides the mirrored
endpoint from Home Assistant.

== Momentary button events

Use native ESPHome binary-sensor automations to recognize gestures locally and
publish the resulting HACAN event. `hacan.publish_event` owns its declared
EntityId and endpoint automatically.

[source,yaml]
----
binary_sensor:
  - platform: gpio
    id: living_room_button
    pin: GPIO14
    on_multi_click:
      - timing:
          - ON for at most 400ms
          - OFF for at least 300ms
        then:
          - hacan.publish_event:
              hacan_id: hacan_node
              entity_id: 0x01010001
              endpoint: 0x01
              event: click
----

Available event names are `press`, `release`, `click`, `double_click`, and
`long_press`.

== Switch endpoint

`switch: platform: hacan` owns a local binary `output` and its EntityId. A
local change from Home Assistant or an addressed `COMMAND<bool>` changes the
output and publishes `STATE<bool>`. An acknowledged command returns its actual
validation status; receiving the same command retry does not apply the output
a second time. Optional `state_source_entity_id` subscribes the switch to the
published `STATE<bool>` of another entity. The directory resolves that entity
at runtime; when its state arrives, the switch mirrors the value to its local
output and publishes its own resulting state.

[source,yaml]
----
output:
  - platform: gpio
    id: out01
    pin: GPIO27

switch:
  - platform: hacan
    hacan_id: hacan_node
    entity_id: 0x01020001
    endpoint: 0x02
    output: out01
    state_source_entity_id: 0x01010001
    name: Living room main light
----

The endpoint declarations above register ownership automatically. Multiple
HACAN switches, including switches on different nodes, may use the same
`state_source_entity_id`; every one mirrors the received state independently.

`event_sources` binds recognized button events to local actions. It accepts
multiple entries, including several gestures from one source entity:

[source,yaml]
----
event_sources:
  - entity_id: 0x01010001
    event: click
    action: toggle
  - entity_id: 0x01010001
    event: long_press
    action: turn_off
----

Supported actions are `toggle`, `turn_on`, and `turn_off`.

== Binary light endpoint

`light: platform: hacan` exposes a local binary output as an `ON_OFF` light in
Home Assistant. It accepts `COMMAND<bool>`, publishes `STATE<bool>`, and
supports the same `event_sources` configuration as a HACAN switch. Brightness
will be a future additive extension with a separate numeric endpoint.

== Commissioning roles

`primary` enables the commissioning manager. It discovers nodes and issues
`ADDRESS_ASSIGN` for unassigned NodeUIDs. `none` is the normal role for an
endpoint node. `secondary` is accepted configuration but remains passive in the
first implementation: it does not assign addresses and logs that automatic
failover is not implemented.

On first boot, the sole `primary` persists the reserved bootstrap address
`0x001` and then performs the normal claim procedure. Other nodes receive an
automatically assigned address from that manager.

Only one active `primary` role is supported in an installation. Address conflict
handling remains active on every node, as required by the protocol.

An unassigned node also initiates commissioning itself: it broadcasts
`DISCOVERY_REQUEST` with source address zero after a UID-derived startup delay,
then uses the protocol retry backoff until it receives its `ADDRESS_ASSIGN`.
