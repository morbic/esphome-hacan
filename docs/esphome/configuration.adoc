= ESPHome YAML configuration
:toc: left
:sectnums:

This page specifies the available configuration interface for the HACAN base
component.

== Central entity registry

An installation keeps the alias-to-identifier registry in one YAML file. It is
included using standard ESPHome packages and substitutions. ESPHome expands the
substitution before validating the HACAN configuration; the component therefore
receives a numeric identifier and has no YAML registry parser.

[source,yaml]
----
# installation/entities.yaml
substitutions:
  hacan_living_room_main_light_switch: "0x01010001"
  hacan_living_room_main_light: "0x01020001"
----

The registry is a build-time installation artifact. It contains neither node
identity nor endpoint ownership and is never transmitted or refreshed at
runtime. Installation policy should prohibit local redefinition of these
substitutions.

== Base component

[source,yaml]
----
packages:
  hacan_entities: !include installation/entities.yaml

hacan:
  canbus_id: hacan_bus
  commissioning_role: primary  # primary | secondary | none
  owned_entities:
    - endpoint: 0x01
      entity_id: ${hacan_living_room_main_light_switch}
  observed_entities:
    - entity_id: ${hacan_living_room_main_light}
----

`NodeUID` is derived deterministically from the ESP32 factory MAC address. No
YAML override is provided in the first implementation. A `NodeAddress` is
assigned by commissioning and persisted locally by the component.

`owned_entities` configures the `ENTITY_CLAIM` assignments made by this node.
`observed_entities` identifies mappings that the node restores through
`ENTITY_RESOLVE`. After commissioning, the runtime emits one resolve request
per main-loop iteration for each configured observed entity. An owning node
answers with a fresh `ENTITY_CLAIM`, which restores the volatile mapping.

Each list accepts at most 16 declarations. This bound is checked during YAML
validation and matches the fixed-capacity storage in the component and runtime.
Future HACAN endpoint platforms register the same declarations automatically;
these lists remain a low-level option for endpoints without a dedicated
platform.

== Commissioning roles

`primary` enables the commissioning manager. It discovers nodes and issues
`ADDRESS_ASSIGN` for unassigned NodeUIDs. `none` is the normal role for an
endpoint node. `secondary` is accepted configuration but remains passive in the
first implementation: it does not assign addresses and logs that automatic
failover is not implemented.

On first boot, the sole `primary` persists the reserved bootstrap address
`0x001` and then performs the normal claim procedure. Other nodes receive an
automatically assigned address from that manager.

Only one active `primary` role is supported in an installation. Address conflict
handling remains active on every node, as required by the protocol.

An unassigned node also initiates commissioning itself: it broadcasts
`DISCOVERY_REQUEST` with source address zero after a UID-derived startup delay,
then uses the protocol retry backoff until it receives its `ADDRESS_ASSIGN`.
